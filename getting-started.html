Getting Started

C is small, fast, and close to the machine. It's the language underneath operating systems, databases, game engines and the interpreters for most other languages. In this lesson you'll write your first program, see what actually happens when you build it, and learn to read the compiler's complaints.

What C is, and why learn it

C was created by Dennis Ritchie at Bell Labs in the early 1970s to write the Unix operating system. Half a century later it's still everywhere: the Linux kernel, the Python and Ruby interpreters, SQLite, Git, the firmware in your router and your microwave. When something has to be fast, small, or talk directly to hardware, it's very often written in C.

C is a compiled language. You write human-readable source code in a .c file, and a program called a compiler translates it into machine code that your CPU runs directly. There's no interpreter or virtual machine in between, which is a large part of why C is fast.

C is also a small language. There are only a few dozen keywords, and almost nothing happens behind your back: no garbage collector, no hidden copies, no exceptions. That makes it a superb language for learning how computers really work, because what you write is close to what the machine does. The flip side is that C trusts you completely. It won't stop you from reading past the end of an array or using memory you've already given back. Much of this course is about understanding those sharp edges so they never cut you.

Which C?

C is defined by an ISO standard that gets revised every so often: C89, C99, C11, C17, C23. This course targets C17, and every example here is compiled with -std=c17 -Wall -Wextra, which turns on a sensible set of warnings. Where something is undefined or implementation-defined by the standard, we'll say so explicitly.

Hello, world

By long tradition, the first program you write in a new language prints a greeting. Press Run:

Six lines, and every one of them matters. Let's go through them.

#include <stdio.h>

Lines starting with # are instructions to the preprocessor, which runs before the compiler proper. #include means "paste the contents of this file here". stdio.h is the standard input/output header: it tells the compiler that a function called printf exists, what arguments it takes, and what it returns. Without it, the compiler doesn't know what printf is.

The angle brackets mean "look in the system's standard header directories". You'll later write your own headers and include them with quotes, like #include "mylib.h".

int main(void)

Every C program has exactly one function called main, and that's where execution begins. The int before the name says main gives back an integer when it finishes. The (void) says it takes no arguments. (You'll sometimes see int main(); in C17, empty parentheses mean something subtly different from (void), so we always write void.)

The curly braces { } mark the body of the function: the statements that run when it's called.

printf("Hello, world!\n");

This calls the function printf ("print formatted") with one argument, the string literal "Hello, world!\n". Text in double quotes is a string. printf writes it to standard output, which is normally your terminal (here, the output panel).

The \n is an escape sequence: a backslash followed by a character, standing for something you can't easily type inside a string. \n means newline. printf does not add a newline for you, so without it the next thing printed would continue on the same line. A few other escapes you'll meet:

EscapeMeaning
\nnewline
\ttab
\"a literal double quote inside a string
\\a literal backslash

Finally, the semicolon. In C, a statement ends with ;. Line breaks mean nothing to the compiler; the semicolon is what tells it one statement is over. Forgetting one is the most common error you'll ever make, and we'll deliberately make it below.

return 0;

This ends main and hands the value 0 back to whoever started the program, usually the operating system or your shell. By convention, 0 means "success" and any other value means something went wrong. Scripts and build tools rely on this, so it's a good habit to return it explicitly. (Strictly, C lets you leave it out of main only, and then behaves as if you'd written return 0;, but being explicit is clearer.)

From source code to running program

When you press Run, quite a lot happens. Your .c file is plain text; your CPU can't execute it. Building it into a program is a pipeline of three main stages:

StageWhat it doesProduces
1. PreprocessHandles every # line: pastes in #included headers, expands macros, strips comments.One big expanded C source file
2. CompileChecks your code against the rules of C, reports errors and warnings, and translates it into machine code for your CPU.An object file (hello.o)
3. LinkJoins your object file with the code for library functions you used, like printf, which lives in the C standard library.An executable (hello)

On your own machine, with a compiler such as gcc or clang installed, one command runs all three stages:

gcc -std=c17 -Wall -Wextra hello.c -o hello
./hello
Hello, world!

-o hello names the output file (without it you get the oddly named a.out). -Wall -Wextra turns on warnings, which you always want. ./hello runs the program from the current directory. On Windows the executable would be hello.exe.

The Run button on this site does exactly the same thing, just remotely: it sends your code to Compiler Explorer, which compiles it with gcc using those same flags, runs the program, and sends back the compiler messages and the output.

Compile time vs run time

This distinction comes up constantly. Compile-time errors are found by the compiler before your program ever runs: a missing semicolon, a misspelled function name. Run-time errors happen while the program is running: dividing by zero, reading memory you shouldn't. The compiler can catch the first kind for you, so treat its warnings as free bug reports.

Reading a compiler error

Everyone writes code that doesn't compile. Learning to read the error quickly is one of the most valuable skills you can build. The program below is missing a semicolon. Run it before fixing it and look at the message:

gcc will say something like:

broken.c: In function 'main':
broken.c:4:40: error: expected ';' before 'return'
    4 |     printf("Something is missing...\n")
      |                                        ^
      |                                        ;
    5 |     return 0;
      |     ~~~~~~

Here's how to read it:

  • broken.c:4:40 is the file, line and column where the compiler noticed the problem. (On this site the file is called <source>, which is what Compiler Explorer names it.)
  • error: means the program can't be built. A warning: means it can be built, but the compiler thinks something is probably wrong.
  • The message says what it expected: a ; before return.
  • The caret ^ points at the spot, and gcc even suggests the fix.

Now fix it: add the semicolon at the end of the printf line and run again.

The error is often reported on the next line

The compiler only realises a semicolon is missing when it sees something that can't continue the statement, here return on line 5. So the reported location is sometimes after the real mistake. If a line looks fine, check the end of the one before it.

Two more habits that save hours:

  • Fix the first error first. One mistake can confuse the compiler into reporting a cascade of bogus errors after it. Fix the top one, recompile, and many of the rest often vanish.
  • Don't ignore warnings. A warning is the compiler telling you your code is legal but probably not what you meant. In C, "legal but wrong" is where the nastiest bugs live.

Printing numbers with printf

The f in printf stands for formatted. The first argument is a format string, and it can contain conversion specifiers, placeholders starting with %, that get replaced by the extra arguments, in order. %d means "print an int as a decimal number":

The specifiers must match the arguments

printf trusts you to pass one argument of the right type for each specifier. Too few arguments (printf("%d %d\n", 1);) or the wrong type (printf("%d\n", 3.5);) is undefined behaviour: it may print garbage, or worse. Compilers warn about this with -Wall, which is one more reason to keep warnings on. You'll meet specifiers for other types (%f, %c, %s…) in the next lesson.

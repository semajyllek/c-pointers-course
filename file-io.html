File I/O

Everything your programs have done so far vanishes when they exit. Files let a program keep data between runs, read input that's far too big to type, and produce output other programs can use. In C, all of it goes through one small set of functions in <stdio.h>, built around a pointer type called FILE *.

About the examples on this page

The runnable examples execute in a temporary sandbox that has no files of yours in it. So each one first writes a small file (like notes.txt) and then reads it back in the same program. Snippets that assume a file already exists are shown read-only.

Streams and FILE *

C doesn't talk to files directly. It talks to streams: a source or destination of bytes, which might be a file on disk, the terminal, or a pipe from another program. A stream is represented by a FILE object that the library manages for you. It holds a buffer, your current position in the file, and flags recording whether you've hit end-of-file or an error.

You never create a FILE yourself or look inside one. You get a FILE * from fopen, pass it to the reading and writing functions, and hand it back with fclose. The pattern is always the same:

Opening a file: fopen and modes

FILE *fopen(const char *path, const char *mode); takes a file name (relative to the program's current directory, or an absolute path) and a mode string saying what you intend to do:

ModeMeaningIf the file existsIf it doesn't
"r"readread from the startfails (returns NULL)
"w"writeerases it (truncates to 0 bytes)creates it
"a"appendevery write goes to the endcreates it
"r+"read and writestarts at the beginning, keeps contentsfails
"w+"read and writeerases itcreates it
"a+"read and appendreads anywhere, writes go to the endcreates it

Add a b ("rb", "wb", "r+b"...) to open in binary mode. On Linux and macOS text and binary mode behave identically. On Windows, text mode translates "\r\n" line endings to '\n' and back, which would corrupt non-text data. Rule of thumb: use b whenever the file isn't human-readable text. Since C11 you can also add x to a write mode ("wx") to fail instead of overwriting an existing file.

"w" destroys the file immediately

Opening with "w" truncates the file to zero length the moment fopen succeeds, before you've written anything. Opening your input file with "w" by mistake is a classic way to lose data. If you want to add to a file, use "a".

Always check for NULL

fopen fails more often than you'd think: the file doesn't exist, the name has a typo, you lack permission, the directory doesn't exist. When it fails it returns NULL and sets errno to a code describing why. perror (from <stdio.h>) prints your message followed by a readable description of that code:

That prints something like could not open no-such-file.txt: No such file or directory to the error stream. Passing a NULL FILE * to any other stdio function is undefined behaviour, usually a crash, so this check is not optional.

Writing text: fprintf, fputs, fputc

The writing functions are the ones you know, with an f in front and a FILE * argument:

FunctionWritesReturns on error
fprintf(f, "x=%d\n", x)formatted text, exactly like printfa negative number
fputs("hello\n", f)a string, without adding a newline (unlike puts)EOF
fputc('A', f)one characterEOF

Notice that fputs and fputc take the stream last, while fprintf takes it first. Here is a complete round trip: write a file, close it, open it again for reading, and print what's in it.

Why fclose matters

Writes are buffered: fputs usually copies your bytes into the FILE's memory buffer, and the library only hands them to the operating system when the buffer fills up, when you call fflush(f), or when you call fclose(f). That's much faster than a system call per character, but it means:

  • If you forget to close a file you wrote, the last chunk may never reach the disk if the program crashes or calls abort. (A normal return from main or exit does flush open streams, but relying on that is sloppy.)
  • An error such as a full disk might only be discovered when the buffer is flushed, so fclose returns EOF on failure. In programs where the output matters, check it.
  • Each open file uses an operating-system resource, and there's a limit on how many you can have open at once. Close files as soon as you're done.

After fclose(f), the pointer f is dangling, just like after free. Don't use it again.

Reading lines: fgets

char *fgets(char *buf, int size, FILE *f) is the workhorse for reading text. It reads characters into buf until one of three things happens:

  1. it has read a newline (which it keeps in the buffer),
  2. it has read size - 1 characters (leaving room for the '\0'), or
  3. it hits end-of-file.

It always null-terminates the result, and returns buf on success or NULL if it couldn't read anything (end of file, or an error). That return value is what you loop on. Because of rule 2, a line longer than the buffer comes back in several pieces, and only the last piece ends with '\n'. Use a generous buffer, and if you need the line without its newline, chop it off with strcspn:

strcspn(line, "\n") returns the index of the first '\n', or the string's length if there isn't one, so the assignment is safe either way.

Reading characters: fgetc and EOF

int fgetc(FILE *f) reads one character. Look carefully at the return type: it's int, not char. On success, fgetc returns the byte as an unsigned char value (0 to 255) converted to int. On end-of-file or error, it returns the macro EOF, a negative int (almost always -1) that can't be confused with any real byte. This is the idiomatic loop:

Read (c = fgetc(f)) != EOF from the inside out: call fgetc, store the result in c, then compare that stored value to EOF. The extra parentheses are required because != binds tighter than =. Without them you'd store the comparison result (0 or 1) in c.

Why char c breaks the loop

fgetc can return 257 different values: the 256 possible bytes plus EOF. A char only holds 256, so something has to give. If char is unsigned on your platform (it is on many ARM systems), c can never equal -1 and the loop never ends. If char is signed, a perfectly valid byte 0xFF becomes -1 and is mistaken for end-of-file, cutting the read short. Always store the result in an int.

Why while (!feof(f)) is wrong

It looks natural to write "while not at the end of the file, read a line". But feof(f) doesn't look ahead. It only reports that a previous read has already tried to go past the end and failed. So the loop always runs one extra time, and that last read fails. Watch the last line get printed twice:

After reading "last\n", fgets stopped at the newline and never touched the end of the file, so feof is still false. The fourth fgets finds nothing, returns NULL and sets the end-of-file flag, but the loop body has already started and prints the stale buffer. With fgetc the same mistake would process EOF as if it were a character.

The fix is the pattern you've already seen: make the read itself the loop condition, and check its return value. Then use feof and ferror after the loop, for what they're actually for: finding out why reading stopped.

Reading formatted data: fscanf

fscanf is scanf for any stream. Its return value is the number of items it successfully converted (or EOF if input ended before the first one), so you loop for as long as you get everything you asked for:

Two habits make fscanf safe:

  • Compare against the exact count you expect (== 2 here), not just "not EOF". If a line contained dave abc, fscanf would return 1, and you'd want to stop rather than use a garbage score.
  • Always give %s a width: %31s for a 32-byte buffer, leaving room for the '\0'. A bare %s will write past the end of your array if the file contains a long word.

For messy or untrusted input, a sturdier approach is to read whole lines with fgets and then pick them apart with sscanf (scan from a string) or strtol. A malformed line then can't knock the rest of the file out of step.

stdin, stdout and stderr are FILE *s too

Every C program starts with three streams already open, declared in <stdio.h>:

StreamNormally connected toUsed by
stdinthe keyboard (or piped input)scanf, getchar
stdoutthe terminalprintf, puts, putchar
stderrthe terminalperror, and your error messages

So printf(...) is just fprintf(stdout, ...), and fgets(buf, sizeof buf, stdin) reads a line typed by the user. That means any function you write that takes a FILE * works on files and on the terminal:

Why errors go to stderr

Both stdout and stderr show up in your terminal, so why have two? Because the shell can redirect them separately. When someone saves your program's output to a file, they still want to see the error messages, and they definitely don't want them mixed into the data:

./report > report.txt 2> errors.txt

Here > sends stdout to report.txt and 2> sends stderr (stream number 2) to errors.txt. There's also a buffering difference: stdout is usually line-buffered on a terminal (and fully buffered when redirected), while stderr is unbuffered, so an error message appears immediately even if the program crashes a moment later. Pair error messages with a non-zero exit status, such as return EXIT_FAILURE;, so scripts can tell that something went wrong.

Binary files aren't portable

The bytes you write are exactly how this compiler on this machine lays out the struct: its padding, the size of int, and the byte order (endianness). A file written on one system may be garbage when read on another. And never fwrite a struct that contains pointers: the file would store addresses, which mean nothing the next time the program runs. For data that must travel, use text (like CSV or JSON) or write each field in a defined byte order.

Moving around: fseek, ftell, rewind

Every open stream has a file position: where the next read or write happens. Reading and writing advance it automatically, but you can also move it yourself:

CallEffect
fseek(f, offset, SEEK_SET)move to offset bytes from the start
fseek(f, offset, SEEK_CUR)move offset bytes from the current position (may be negative)
fseek(f, offset, SEEK_END)move relative to the end of the file
ftell(f)return the current position as a long (or -1 on error)
rewind(f)go back to the start and clear the error/EOF flags

A few fine points. When a stream is open for both reading and writing, you must call fseek, rewind or fflush between a write and a following read, which is why the example seeks before its first fread. In text mode, ftell's value is only guaranteed to be something you can pass back to fseek, not necessarily a byte count (Windows line-ending translation is the reason), so measure sizes in binary mode. And remove(path), also from <stdio.h>, deletes a file.

A checklist for robust file code

  • Check every fopen for NULL, and report the reason with perror (to stderr).
  • Use the read function's return value as the loop condition: fgets(...) != NULL, (c = fgetc(f)) != EOF, fscanf(...) == expected, fread(...) == count.
  • Store fgetc's result in an int.
  • Give every %s a width, and size buffers with sizeof buf.
  • Use "rb"/"wb" for non-text data.
  • Close every file you open, exactly once, and don't touch the FILE * afterwards.

Exercises

Write numbers, then sum them

Write the numbers 1 to 5 into numbers.txt, one per line. Close the file, open it again for reading, read the numbers back with fscanf, and print sum = 15. Check both fopen calls.

Hint

Write with fprintf(f, "%d\n", i); in a loop. To read, while (fscanf(f, "%d", &n) == 1) sum += n;. %d skips the newlines for you.

Count lines, words and characters

The starter writes a short text to text.txt. Read it back one character at a time with fgetc and count the lines (newline characters), words (runs of non-whitespace characters) and characters, then print them in the format lines=L words=W chars=C.

Hint

Keep a flag in_word. For each character: if isspace(c), set in_word = 0; otherwise, if in_word was 0, you've found the start of a new word, so count it and set in_word = 1. Note the extra spaces in "jumps over": they must not create extra words. Remember int c.

Copy a file

Write long copy_file(const char *src, const char *dst), which copies src to dst byte by byte (open both in binary mode) and returns the number of bytes copied, or -1 if either file can't be opened. Make sure it closes everything it opened, even on failure. The provided main creates the source, copies it, and prints the copy.

Hint

Open src first and return -1 if it fails. Then open dst; if that fails, fclose(in) before returning. Copy with while ((c = fgetc(in)) != EOF) { fputc(c, out); count++; }, then close both.

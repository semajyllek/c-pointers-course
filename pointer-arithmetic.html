Pointer Arithmetic

A pointer holds an address, and addresses are numbers, so C lets you add to them and subtract them. But pointer arithmetic doesn't count in bytes. It counts in elements: p + 1 means "the next one of whatever p points to". That rule is what lets a pointer walk through an array.

p + 1 moves by one element

In the Arrays lesson you saw that array elements sit right next to each other in memory, sizeof bytes apart. Suppose p points to one of them. Then:

  • p + 1 is the address of the next element: sizeof *p bytes further on.
  • p + n is n elements on, which is n * sizeof *p bytes.
  • p - 1 is the previous element.

The compiler does the multiplication for you, using the pointer's type. That's the other big reason pointers have types (the first, from Pointer Basics, was knowing how many bytes *p reads). Run this and compare each pair of addresses:

*p++ versus (*p)++

Pointer loops are often written compactly with *p++, and its look-alikes do quite different things. The rule: postfix ++ binds more tightly than unary *, while prefix ++ and * apply right to left.

ExpressionMeansValue of the expressionChanges
*p++*(p++)the element p pointed to beforep moves to the next element
(*p)++increment the pointed-to valuethe element's old valuethe element goes up by 1; p stays put
*++p*(++p)the next elementp moves first
++*p++(*p)the element's new valuethe element goes up by 1

*p++ is idiomatic: "use this element, then move on". It's the heart of many classic C loops, such as copying a string: while (*src != '\0') { *dst++ = *src++; }. If you ever mean "increment the value", write the parentheses: (*p)++.

Subtracting pointers

Subtracting one pointer from another (both into the same array) gives the number of elements between them, not the number of bytes. The result has type ptrdiff_t, a signed integer type defined in <stddef.h>, and you print it with %td.

That makes pointer subtraction the way to turn a pointer back into an index: p - &a[0] is the index of the element p points at. It's also why end - start is a length: for a one-past-the-end end, it's exactly the number of elements.

The rule is that both pointers must point into (or one past the end of) the same array. Subtracting pointers into two unrelated arrays is undefined: they aren't guaranteed to be any particular distance apart, so the answer would be meaningless.

Comparing pointers

  • == and != work on any two pointers of compatible type: are they the same address? (Comparing with NULL is the most common case.)
  • <, <=, >, >= are only defined for pointers into the same array (or one past its end). p < q then means "p points to an earlier element than q".

The rules: staying inside the array

Pointer arithmetic is only defined while you stay within one array. Precisely, for an array of N elements:

PointerCompute it?Compare it?Dereference it?
&a[0] … &a[N-1]yesyesyes
&a[0] + N (one past the end)yesyesno
anything before &a[0] or beyond one past the endnonono

The special one-past-the-end address exists so that loops like while (p != end) have something to stop at. A plain variable counts as an array of one element for these rules, so &x + 1 is a valid one-past-the-end pointer too.

Just computing an out-of-range pointer is undefined

It's tempting to think a pointer is "only dangerous when you dereference it". The standard is stricter: creating a pointer outside the array (other than one past the end) is already undefined behaviour. In practice the classic bug is a backward loop like for (p = end - 1; p >= &a[0]; p--), whose last p-- steps to before the start. On most machines it happens to work, but optimisers are allowed to assume it never happens, and occasionally they break such code. Walk backwards by decrementing before use instead: for (p = end; p != &a[0]; ) { p--; … }.

What you can't do

  • Add two pointers. p + q is a compile error. An address plus an address has no meaning (what's your house number plus your neighbour's?). Pointer minus pointer is fine, and gives a count.
  • Multiply or divide pointers, or use % on them: compile errors.
  • Arithmetic on void *. A void * is an address with no element type (you'll meet it properly in Advanced Pointers), so the compiler doesn't know how far + 1 should move. Standard C forbids it.
GCC and Clang allow void * arithmetic anyway

As a non-standard extension, GCC and Clang treat void * arithmetic as if it were on char * (moving by bytes), and by default they don't even warn. Code that relies on it won't compile with other compilers, such as MSVC. Compile with -Wpointer-arith (or -pedantic) to be warned, and convert to unsigned char * when you genuinely want to move byte by byte.

Indexing a pointer

One last connection. Because *(p + i) is so common, C gives it a shorter spelling: p[i]. In fact, that's how the language defines the subscript operator: E1[E2] means *((E1) + (E2)). So p[2] works on a pointer just as it does on an array, and it's two elements past wherever p is pointing. The next lesson, Pointers & Arrays, picks up exactly here and shows why a[i] and *(a + i) are the same thing.

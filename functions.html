Functions

A function is a named, reusable piece of code: you hand it some values, it does its job, and it can hand one value back. Every C program you've written so far already has one, main. This lesson is about writing your own, and about what really happens in memory when one function calls another.

Why bother with functions?

Imagine a program that needs the larger of two numbers in five different places. You could copy the same if/else five times, but then a bug has to be fixed five times, and every reader has to work out five times what that block of code is for. A function fixes all three problems at once:

  • No repetition. Write the logic once, use it everywhere.
  • A name. max(a, b) says what it does; ten lines of comparisons don't.
  • Small, testable pieces. You can check that max works on its own and then stop thinking about how it works.

The body in braces is the code that runs on each call. return result; ends the function immediately and sends result back to the caller, so square(4) is an expression whose value is 16. You can store it in a variable, pass it straight to printf, or use it inside a bigger expression like square(3) + square(4).

Two words worth keeping straight: the variables in the header (n) are parameters; the values you pass in a call (4, 9) are arguments. Each argument is converted to its parameter's type, as if by assignment, so square(2.9) would pass 2.

Several parameters

Parameters are separated by commas, and each needs its own type, even when they're all the same type. int max(int a, b) is a syntax error.

Notice that max has two return statements. The first one that runs wins, and nothing after it in the function executes. That's why no else is needed.

void: no value, no parameters

Some functions do something (print, update a counter) rather than compute a value. Their return type is void, which means "returns nothing". A void function can use a bare return; to leave early, or simply run off the end of its body.

void in the parameter list, as in greet(void) and main(void), means "takes no arguments". You still need the parentheses when calling it: greet();. Writing just greet; names the function without calling it, and the compiler will warn that the statement does nothing.

f(void) versus f()

In C17, empty parentheses in a declaration mean "takes some unspecified arguments", an old-style form that turns off argument checking. In C23 they finally mean the same as (void). Writing (void) is correct under every standard, so it's the habit this course uses.

Don't fall off the end of a non-void function

If a function is declared to return int but control reaches the closing brace without a return, and the caller uses the result, the behaviour is undefined: you get whatever garbage was lying around. -Wall warns about this ("control reaches end of non-void function"), so treat that warning as an error. The one exception is main, which returns 0 if it reaches its closing brace.

Declaration vs definition, and why order matters

The C compiler reads your file from top to bottom, once. When it reaches a call like square(4), it must already know what square is: what it returns, and what parameters it takes. So this program doesn't compile. Press Run to see the error:

You can fix it by moving square above main, but in bigger programs functions call each other in every direction and there may be no order that works. The real fix is a declaration, also called a prototype: the function header followed by a semicolon instead of a body.

  • A declaration tells the compiler the function's name, return type and parameter types. That is all it needs to check a call and generate code for it.
  • A definition is the declaration plus the body. There must be exactly one.

Parameter names are optional in a prototype (int square(int); is fine), but including them documents what each argument is for. The prototype and definition must agree on types, or the compiler reports a conflict. A common layout is: #includes, then prototypes for every function, then main, then the other definitions. In fact, that's what #include <stdio.h> is doing for you: the file is full of prototypes, including one for printf (it returns an int, the number of characters printed), which is how the compiler can check your printf calls even though you never wrote that function.

Pass by value: the function gets a copy

This is the single most important rule about C functions, and it surprises almost everyone. When you call a function, each argument's value is copied into a brand-new parameter variable. The function works on the copy. Whatever it does to that copy, the caller's variable is untouched.

Cliffhanger: what if you need to change the caller's variable?

A function returns at most one value. So how would you write swap(a, b), which must change two of the caller's variables? With pass by value alone, you can't. The answer is to pass the variables' addresses instead of their values, which is exactly what pointers are for. You'll learn what an address is in Pointer Basics, and write a working swap in Pointers & Functions.

Scope and lifetime

Two questions about every variable: where in the code can I use its name? (its scope) and when does its memory exist? (its lifetime).

Local variables

A variable declared inside a function, including its parameters, is local. Its name is only visible from the declaration to the end of the enclosing { } block, and its memory lives only while that block is running. Each call gets a fresh set, which is why two functions can both have a variable called i or n without any conflict: they're different variables in different frames.

Local variables are not automatically initialised. int total; holds whatever bytes were left in that piece of memory, so always give a local a value before you read it.

Global variables (use sparingly)

A variable declared outside every function is global: visible from its declaration to the end of the file, alive for the whole run of the program, and initialised to zero if you don't give it a value.

That looks convenient, and it's tempting as a way around pass by value. Resist it for most things. Any function can change a global, so when its value is wrong you have to inspect every function to find out who did it, and a function that depends on a global can't be understood or tested on its own. Globals are fine for genuine program-wide constants and the occasional shared setting; for passing data around, use parameters and return values.

static locals: private memory that persists

The call stack

You've now seen the stack twice in the visualizer. Here is the full picture. Each time a function is called, the program pushes a new frame onto the call stack holding that call's parameters, its local variables and the place to return to. When the function returns, its frame is popped and the memory is reused by the next call. The function on top is always the one currently running; the ones beneath it are waiting for their calls to finish.

That's why local variables vanish when a function returns: their frame is gone. (It's also why, in Pointers & Functions, you'll see that returning the address of a local variable is a serious bug.)

Recursion

A function can call itself. That's recursion, and it fits problems that contain smaller copies of themselves. The factorial of n is n × (n−1) × … × 1, which you can also say as: factorial(n) is n * factorial(n - 1), and factorial(1) is 1. Every recursive function needs both halves of that:

  • A base case that answers directly without recursing (n <= 1 gives 1).
  • A recursive case that calls itself on a smaller problem, so it's guaranteed to reach the base case eventually.

Each recursive call is an ordinary call: it gets its own frame with its own n. Step through and watch three factorial frames stack up, then unwind as each one returns its answer to the one below.

A missing base case overflows the stack

If a recursive function never reaches its base case (you forgot it, or the recursive call doesn't make the problem smaller), it keeps pushing frames until the stack, typically just a few megabytes, runs out. The program then crashes, usually with a "segmentation fault" or "stack overflow". The same thing can happen with correct code given a huge input, which is one reason simple loops are often preferred in C. Anything you can write recursively you can also write with a loop.

Common mistakes

  • Expecting a parameter change to stick. Assigning to a parameter changes only the copy. Return the new value instead.
  • Ignoring the return value. square(5); on its own line computes 25 and throws it away. Store it or use it.
  • Integer division in a "helper". int average(int a, int b) { return (a + b) / 2; } truncates. If you want 2.5, the return type and the arithmetic both need to be double.
  • Calling before declaring. Put a prototype at the top of the file.
  • Missing return on some path of a non-void function. Read your -Wall warnings.

The largest of three

Write a function int max3(int a, int b, int c) that returns the largest of its three arguments. main is already written for you. For an extra challenge, write a two-argument max2 first and build max3 out of it.

Hint

Keep a variable int best = a;, then replace it with b if b is bigger, and with c if c is bigger. Return best. Make sure the function is defined above main (or add a prototype).

Power, with a prototype

Write int power(int base, int exp) that returns base raised to exp (assume exp >= 0; anything to the power 0 is 1). Use a loop, not the pow library function. The catch: the definition must go below main, so you'll need a prototype above it.

Hint

The prototype is the header plus a semicolon: int power(int base, int exp);. In the definition, start with int result = 1; and multiply it by base, exp times. If exp is 0 the loop never runs and you return 1, which is exactly right.

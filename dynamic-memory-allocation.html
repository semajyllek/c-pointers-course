Dynamic Memory

So far, every variable you've made has had its size fixed when you wrote the code and its lifetime tied to the function it lives in. Real programs need more: a list as long as the user's input, or data that outlives the function that created it. That's what the heap is for. You ask for memory with malloc, and you give it back with free. In between, its care is entirely your job.

Stack vs heap

Your program's memory is divided into regions. Two matter here:

  • The stack holds local variables. Each function call pushes a frame; returning pops it. It's fast and automatic, which is exactly why returning a pointer to a local is a bug (you saw that last lesson). It's also fairly small, often 1–8 MB in total.
  • The heap is a large pool you manage by hand. Memory you get from it stays allocated until you explicitly free it, no matter which functions return in the meantime. Its size is limited mostly by your machine's memory.

malloc: asking for memory

malloc (from <stdlib.h>) takes a number of bytes and returns a pointer to a fresh block of at least that size, or NULL if it can't. Its return type is void *, a "pointer to anything", which C converts to your pointer type automatically.

Three habits are packed into that code, and each one prevents a real bug:

  1. n * sizeof *a, not n * sizeof(int). sizeof *a means "the size of whatever a points to". It's computed at compile time (nothing is dereferenced), and if you later change a to double *, the allocation stays correct automatically. Writing sizeof a (the pointer, 8 bytes) instead is a classic mistake.
  2. Always check for NULL. Allocation can fail, and writing through a NULL pointer is undefined behaviour. On a desktop it's rare, but a huge or miscalculated size makes it happen instantly.
  3. No cast. In C, void * converts implicitly, so int *a = (int *)malloc(…) is unnecessary. (C++ requires the cast; that's where you may have seen it.)
malloc'd memory is not initialised

The bytes in a fresh malloc block are whatever happened to be there. Reading them before writing is a bug, just like reading an uninitialised local. If you need zeros, use calloc.

calloc: allocate and zero

calloc(count, size) allocates room for count objects of size bytes each and sets every byte to zero. For integers that means every element is 0.

A bonus: calloc checks that count * size doesn't overflow and returns NULL if it would, while malloc(count * size) silently wraps around to a tiny number if the multiplication overflows.

free: giving it back

Every block you get from malloc, calloc or realloc must be passed to free exactly once when you're done with it. The rules:

  • Pass free the exact pointer the allocator gave you, not a pointer into the middle of the block, and never the address of a stack variable.
  • free(NULL) is allowed and does nothing.
  • After free(p), the value in p is unchanged, but it no longer points to anything you own. It's a dangling pointer.

That last point is why many programmers write free(p); p = NULL;. Now an accidental second free(p) is harmless, and an accidental *p crashes immediately instead of silently corrupting memory.

realloc: resizing a block

realloc(p, new_size) changes the size of a block you already own. It returns a pointer to the resized block, which may be the same address (if there was room to grow in place) or a new one (as in the visualizer above, where it copied the contents and freed the old block). Contents up to the smaller of the old and new sizes are preserved; any extra space is uninitialised. Two details are worth knowing: realloc(NULL, size) behaves like malloc(size), and if it fails, it returns NULL and leaves the original block untouched.

A growable array

Put it all together and you get the most useful data structure there is: an array that grows as you add to it. Keep three things: the pointer, how many elements are in use (len), and how many fit (cap). When len reaches cap, double the capacity.

Change the input and run it again: add more numbers and the array keeps growing. Why double instead of adding one slot at a time? Each realloc may copy every element. Growing by one would copy 1, then 2, then 3… elements, which adds up to roughly n²/2 copies for n items. Doubling means copies happen rarely, and the total work stays proportional to n. This is how C++'s vector, Python's list and Java's ArrayList work under the hood.

The classic bugs

Manual memory management fails in a small number of well-known ways. Learn to recognise them:

  • A leak doesn't crash; the memory just stays reserved until the program exits (the OS reclaims everything then). For a short program it's harmless, but in a server or a game loop it grows until the machine runs out.
  • Use-after-free and double free are worse: they're undefined behaviour, and they're among the most common sources of real-world security vulnerabilities.
  • Setting pointers to NULL after freeing turns bugs 2 and 3 into a clean crash or a harmless no-op.
  • Have a clear owner for every allocation: one place in the code responsible for freeing it. When a function returns heap memory, say so in a comment ("caller must free").
Let tools find these for you

Memory bugs are notoriously hard to spot by reading code, so use tools. Compile with AddressSanitizer, gcc -g -fsanitize=address prog.c (Clang supports the same flag), and your program stops with a detailed report, including the exact line, the moment it overflows a buffer, uses freed memory or frees twice. It reports leaks at exit too (on Linux). On Linux, Valgrind (valgrind --leak-check=full ./prog) does similar checks without recompiling. These run on your own machine; the Run button on this site can't show them.

Exercises

Read n numbers, print them reversed

The first number of input is n, followed by n integers. Allocate exactly enough memory for them with malloc, read them in, print them in reverse order separated by spaces, and free the memory.

Hint

int *a = malloc(n * sizeof *a); then read with scanf("%d", &a[i]). Print with a loop from i = n - 1 down to 0. Trailing spaces at the end of a line are ignored by the checker.

Write my_strdup

Implement my_strdup: allocate a new heap buffer just big enough for s (including its '\0'), copy the string into it, and return it. Return NULL if allocation fails. main checks that the copy is independent of the original.

Hint

You need strlen(s) + 1 bytes. After checking the result of malloc, copy with strcpy(copy, s) or memcpy(copy, s, n). (Real C libraries provide strdup, and C23 makes it standard, which is why ours is called my_strdup.)

Above average

Read integers until the input ends (you don't know how many there are). Store them in a growable array that starts with capacity 4 and doubles when full. Then print how many numbers were read, and every number that is strictly greater than the average, in input order. To avoid floating point, note that x > sum / count is the same as x * count > sum.

Hint

Inside the loop: if (len == cap) { int *tmp = realloc(data, cap * 2 * sizeof *data); … data = tmp; cap *= 2; } then data[len++] = x;. Afterwards, sum everything into a long, and print each data[i] where (long)data[i] * (long)len > sum. The sum here is 67 and the count is 11, so the average is about 6.09.

Capstone: Linked List

Time to put it all together. In this project you'll build a singly linked list from scratch: a data structure made of heap-allocated nodes chained together by pointers. It uses structs, malloc and free, the -> operator, const, and pointers to pointers, all at once. When you can write one confidently, you really understand pointers.

What is a linked list?

An array stores its elements side by side in one block of memory. A linked list instead stores each element in its own small heap block, a node, and each node holds a pointer to the next one. The list itself is nothing more than a pointer to the first node, usually called head. The last node's next is NULL, which marks the end.

head ──► [ 1 | ●─]──► [ 2 | ●─]──► [ 3 | NULL ]

Compared with an array:

ArrayLinked list
Access element iinstant: a[i]slow: follow i links from the head
Insert or remove at the frontslow: shift every elementinstant: rewire one or two pointers
Growrealloc, which may copy everythingone malloc per new node; nothing moves
Memory overheadnonea pointer per element, plus allocator overhead

In everyday code, a dynamic array is often faster because its elements are contiguous, which modern CPUs love. But linked lists are everywhere in systems code (operating-system kernels, memory allocators, the buckets of a hash table), and building one is the best pointer workout there is.

We'll create every node with a small helper. Exiting on allocation failure keeps the project code short. A library would return NULL or an error code instead and let the caller decide.

Step 2: adding to the front, and printing

Adding a node at the front takes two pointer assignments: point the new node at the current first node, then make head point at the new node. Exercise 1: push_front and print_list

Write push_front (taking struct Node **head) and print_list, which prints every value followed by -> , then NULL and a newline. An empty list prints just NULL.

Hint

push_front is three lines: struct Node *n = new_node(value); n->next = *head; *head = n;. For printing, loop for (const struct Node *p = head; p != NULL; p = p->next), print "%d -> " for each node, and print "NULL\n" after the loop.

Step 3: adding to the back

To append, you have to find the last node (the one whose next is NULL) and attach the new node there. There's one special case: if the list is empty, there is no last node, and the new node becomes the head. That's why push_back also needs struct Node **: sometimes it changes the head.

Look closely at the loop condition: last->next != NULL, not last != NULL. We want to stop on the last node so we can modify its next. Walking until last itself is NULL would leave us holding nothing. Also note that this dereferences last immediately, which is why the empty list has to be handled first.

Cost

push_back walks the whole list, so appending to a list of a million nodes follows a million pointers. Real implementations often keep a second pointer, tail, to the last node, making appends instant at the cost of keeping tail correct in every other operation.

Exercise 2: push_back

Write void push_back(struct Node **head, int value). Handle the empty list, then walk to the last node and attach the new one.

Hint

Create the node first. If *head == NULL, set *head = n and return. Otherwise start struct Node *last = *head;, advance while last->next != NULL, then set last->next = n;. new_node already set n->next to NULL.

Step 4: length and find

Two read-only queries, both using the walking loop. length counts nodes. find returns a pointer to the first node holding a value, or NULL if there isn't one. Returning a pointer, rather than just "yes" or "no", lets the caller read or update the node it found:

Why isn't find's parameter const? Because it returns a non-const pointer into the list. Accepting a const struct Node * and handing back a plain struct Node * would quietly strip the const away. (The C standard library has exactly this wart: strchr takes a const char * and returns a char *.)

Exercise 3: length and find

Write size_t length(const struct Node *head) and struct Node *find(struct Node *head, int value). The provided main uses find's result to change a value in place.

Hint

Both are the walking loop from step 2. length increments a counter for each node. find returns p as soon as p->data == value, and returns NULL after the loop if nothing matched.

Step 5: removing a value (the pointer-to-pointer trick)

To remove a node you have to make whatever pointed at it point past it instead, and then free it. The difficulty is that "whatever pointed at it" is different depending on where the node is:

  • For the first node, it's head itself.
  • For any other node, it's the next field of the node before.

The textbook approach tracks a prev pointer and handles the head as a special case:

It works, but there are two cases to get right and test. Now notice what the two cases have in common: each one overwrites a struct Node * variable, either head or some prev->next. So instead of tracking the previous node, track the address of the pointer that leads to the current node. That's a struct Node **, which we'll call link:

Trace it with the list 1 -> 2 -> 3, removing 2:

  1. link starts as head, i.e. it points at the caller's head variable. *link is the 1-node. Not a match.
  2. link = &cur->next: now link points at the next field inside the 1-node. *link is the 2-node. Match!
  3. *link = cur->next writes into the 1-node's next field, so it now points at the 3-node. The 2-node is unlinked, and we free it.

If the match had been the first node, the very same line would have written into the caller's head. There's no special case, because from link's point of view head and a next field are the same kind of thing: a struct Node * that leads to the rest of the list. Linus Torvalds famously called this version "good taste" in code. The same trick makes push_back shrink to three lines, too: walk link until *link == NULL, then *link = new_node(value);.

Precedence check

&cur->next means &(cur->next), the address of the next field, because -> binds tighter than &. Without the local cur you'd write link = &(*link)->next;, where the parentheses around *link are required.

Exercise 4: remove_value

Write int remove_value(struct Node **head, int value), which removes and frees the first node holding value and returns 1, or returns 0 if no node matches. Try the pointer-to-pointer version. The test removes the head, a middle node, the tail, and a value that isn't there.

Hint

Loop while (*link != NULL). Inside, let struct Node *cur = *link;. On a match: *link = cur->next; free(cur); return 1;. Otherwise advance with link = &cur->next;. Return 0 after the loop. Make sure you unlink before freeing, so you never read cur->next from freed memory.

Step 6: freeing the whole list

Every node came from malloc, so every node must go back with free. Here's the version almost everyone writes first:

The loop's increment step reads p->next after p has been freed. That's undefined behaviour. It often "works" in testing, because the freed memory usually still holds the old bytes, and then fails in production when the allocator reuses the block. The fix is the one you saw in the memory visualizer: save the next pointer before you free.

Finally, after freeing, the caller's head still holds the address of the first (now freed) node: a dangling pointer. If free_list takes a struct Node **, it can set the caller's head to NULL, leaving a valid, empty list behind.

Let the tools check your work

Compile on your own machine with -fsanitize=address -g and AddressSanitizer will stop the program at the exact line of a use-after-free or out-of-bounds access, and report any leaked nodes when the program exits. Valgrind (valgrind ./app) does similar checking on Linux without recompiling. For pointer-heavy code, these tools are indispensable.

Exercise 5: free_list

Write size_t free_list(struct Node **head), which frees every node without any use-after-free, sets the caller's head to NULL, and returns the number of nodes freed. Calling it on an empty list must be safe and return 0.

Hint

Start struct Node *p = *head;. In a while (p != NULL) loop: save struct Node *next = p->next;, then free(p);, then p = next; and count. After the loop, *head = NULL;. An empty list never enters the loop, so it returns 0 naturally.

Where to go next

Congratulations: you've gone from printf("hello") to building and tearing down a heap-allocated data structure with pointers to pointers. Here are some ways to keep going.

Extend your list

  • Reverse it in place by walking the list once and flipping every next pointer. It's a classic interview question and a great box-and-arrow exercise.
  • Make it doubly linked: add a prev pointer so you can walk backwards and remove a node given only a pointer to it.
  • Make it generic: store a void * in each node, and take a comparison function pointer in find and insert_sorted, just like qsort.
  • Split it into files: list.h with the declarations, list.c with the definitions, a test program in main.c, and a Makefile.

Build something bigger

  • A dynamic array ("vector") that grows with realloc, doubling its capacity when full.
  • A hash map from strings to ints: an array of buckets, where each bucket is a linked list like the one you just wrote. Hash the key, pick a bucket, and search its list.
  • A word-frequency counter that reads a text file with fgets and counts words using your hash map.
  • A tiny shell or calculator: read a line, split it into tokens, and dispatch through a table of function pointers.

Use professional tools

  • Compile everything with -Wall -Wextra and, while developing, -fsanitize=address,undefined -g. The sanitizers catch memory errors and undefined behaviour the moment they happen.
  • Learn a debugger: gdb or lldb. Setting a breakpoint and printing *head, then *head->next, is the real-life version of this course's memory visualizer.
  • Run valgrind on Linux to find leaks and invalid reads in existing binaries.

Read more

  • The C Programming Language by Kernighan and Ritchie ("K&R"): short, classic and full of elegant examples. Its style predates modern safety habits, so read it with this course's warnings in mind.
  • Modern C by Jens Gustedt: a thorough, up-to-date treatment of C17 and C23 that's freely available from the author.
  • Effective C by Robert C. Seacord: a practical guide to writing correct, secure C.
  • cppreference.com (its C section) for precise documentation of every library function and language rule, and your system's man pages (man 3 fopen).

Most of all: write programs. Pick something small you'd actually use, build it, break it, and fix it with the sanitizers. That's how C becomes second nature.

Pointers & Arrays

Arrays and pointers are so closely linked in C that people often say "an array is just a pointer". That's not quite true, and the places where it's not true are exactly where bugs hide. This lesson shows you how the two really relate, so array code, string code and function parameters all start making sense.

An array name turns into a pointer

In the last lesson you used pointer arithmetic to walk through memory. Arrays are where that pays off, because of one rule:

The decay rule

In almost every expression, an array's name is automatically converted to a pointer to its first element. For int a[5], using a gives you an int * equal to &a[0]. This conversion is called array-to-pointer decay.

All three addresses are the same. And notice p[2]: you can use square brackets on a pointer, not just on an array. That's not a special convenience; it's how square brackets are actually defined.

a[i] is really *(a + i)

The C standard defines the subscript operator in terms of pointer arithmetic. E1[E2] means exactly *((E1) + (E2)). So when you write a[3]:

  1. a decays to a pointer to a[0].
  2. a + 3 moves forward 3 elements (12 bytes for 4-byte ints), as you learned in Pointer Arithmetic.
  3. * reads the int at that address.

Yes, 2[a] compiles and means the same as a[2], because *(2 + a) is the same as *(a + 2). It's a fun piece of trivia that proves the definition, but never write it in real code.

This also explains why arrays start at index 0: a[0] is *(a + 0), the element right at the start. An index is really an offset from the beginning.

No bounds checking, ever

Because a[i] is just "add and dereference", C never checks that i is in range. a[10] on a 4-element array computes an address past the end and reads whatever is there. That's undefined behaviour: it might print garbage, crash, or quietly work until the day it doesn't.

Where arrays and pointers differ

Decay happens "in almost every expression". The exceptions are what make an array more than a pointer. An array is a block of elements; a pointer is a single variable holding one address. The difference shows up in three places.

1. sizeof sees the whole array

When an array is the operand of sizeof, it does not decay. You get the size of the entire block. A pointer is always just the size of an address (8 bytes on typical 64-bit systems), no matter what it points to.

The sizeof a / sizeof a[0] trick for counting elements only works on a real array, in the scope where it was declared. Use it on a pointer and you get 8 / 4 = 2, which is nonsense. You'll see shortly why that matters for functions.

2. You can't assign to an array

A pointer variable can be pointed somewhere else. An array name can't: the array is its storage, so there's nothing to re-point.

To copy one array into another you copy the elements, with a loop or memcpy from <string.h>.

3. &a is a pointer to the whole array

The other place decay doesn't happen is under &. &a gives the address of the array as a whole, and its type is int (*)[5]: "pointer to an array of 5 ints". It has the same address as &a[0], but a different type, and the type changes what + 1 does:

Look at the last hex digits: a + 1 is 4 bytes along, while &a + 1 is 20 bytes along (0x14 in hex), one whole int[5]. You'll rarely need int (*)[5] yourself, but it explains a confusing compiler message if you ever write int *p = &a; by mistake (just write int *p = a;).

Passing arrays to functions

In the Functions lesson you learned that C passes arguments by value: the function gets a copy. So what happens when you pass an array? The array name decays, so what gets copied is the pointer, not the elements. The function receives the address of the caller's first element.

Two consequences follow:

  • The function can change the caller's array. It has the address of the real elements, not a copy of them.
  • The function has no idea how long the array is. It only has a pointer. You must pass the length separately.

Why sizeof lies inside a function

Since the parameter is a pointer, sizeof on it gives the size of a pointer, not of the array. This is one of the most common beginner bugs in C:

Good compilers warn about this ("sizeof on array function parameter will return size of 'int *'"). The fix is the convention you'll see all over C, including the standard library: pass the length as a separate parameter, and compute it with sizeof in the caller, where the array is still a real array.

Two things to notice. First, the const in const int *a promises that print_all only reads the array; the compiler will stop it from writing a[i] = …. You'll use this a lot in the next lesson. Second, because a function only ever sees a pointer and a length, you can hand it part of an array, like primes + 2.

2D arrays decay too

A 2D array int grid[3][4] is an array of 3 rows, each an int[4]. It decays to a pointer to its first row, of type int (*)[4]. That's why a function taking a 2D array must spell out every dimension except the first: void show(int grid[][4], int rows). The compiler needs the row length to compute grid[r][c].

Walking an array: index vs pointer

There are two common styles for looping over an array. They do the same thing, and modern compilers usually produce identical machine code for both:

In the pointer style, a + n is the address one past the last element. C specifically allows you to compute and compare against that address, as long as you never dereference it. Going any further than one-past-the-end (or before the start) is undefined behaviour, even if you don't dereference.

Which should you use? Index style is clearer in most code, and it's what you should reach for by default. Pointer style shines when the "position" is naturally a pointer: walking a string until '\0', scanning a buffer, or keeping two pointers that move towards each other.

Strings: char[] vs char *

A string is a char array ending in '\0', so everything above applies to strings. But there's one distinction that bites everyone eventually. These two lines look almost identical:

  • greeting is your own array (6 bytes including '\0'). You can change its characters freely. sizeof greeting is 6.
  • literal is a pointer (sizeof literal is 8) to a string literal, which the compiler typically stores in read-only memory and may share between identical literals. You can read it, and you can point literal somewhere else, but you must not modify the characters.
Modifying a string literal is undefined behaviour

For historical reasons string literals have type char[] rather than const char[] in C, so the compiler won't stop you. Protect yourself: whenever a pointer refers to a literal, declare it const char *. Then s[0] = 'j' becomes a compile error. If you need to modify the text, use an array: char s[] = "hello";.

Exercises

Sum with a walking pointer

Finish sum so it returns the total of the n ints starting at a. Don't use square brackets: use a pointer that walks from a up to (but not including) a + n.

Hint

for (const int *p = a; p < a + n; p++) { total += *p; }. The second call passes data + 1, a pointer to the 9, with length 2, so it sums 9 + 27.

Reverse in place with two pointers

Write reverse so it reverses the array in place. Use two pointers: left starting at the first element and right at the last. Swap what they point to, move them towards each other, and stop when they meet.

Hint

The last element is at a + n - 1. Loop while (left < right); inside, swap *left and *right using a temporary int, then left++ and right--.

Your own strlen

Implement my_strlen, which returns the number of characters before the '\0'. Walk a pointer p forward until *p is the terminator, then return how far it moved. (Hint from Pointer Arithmetic: subtracting two pointers into the same array gives the number of elements between them.)

Hint

Start with const char *p = s;, advance with while (*p != '\0') p++;, then return p - s; (cast to size_t to be tidy). For the empty string, the loop never runs and the result is 0.

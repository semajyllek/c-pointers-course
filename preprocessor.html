Preprocessor & Multi-file Programs

Every line starting with # that you've written, starting with #include <stdio.h>, isn't really C. It's an instruction to the preprocessor, a text-processing step that runs before the compiler proper. This lesson shows what it does, how to use macros without getting burned, and how the preprocessor lets you split a program across many files, which is how every real C project is organised.

What the preprocessor does

Before your code is compiled, the preprocessor makes a pass over the source text and:

  • replaces each comment with a single space,
  • carries out directives, the lines beginning with #: pasting in included files, defining macros, keeping or dropping blocks of code, and
  • expands macros: wherever a defined name appears, it substitutes the replacement text.

The crucial thing to understand is that this is text substitution. The preprocessor works on tokens (words, numbers, symbols) and knows nothing about types, variables, scope or functions. The compiler only ever sees the result. You can look at that result yourself with gcc -E, which stops after preprocessing. Given this file:

gcc -E hello.c | tail -n 6
int main(void) {

    for (int i = 0; i < 3; i++)
        puts("hi");
    return 0;
}

The comment is gone, TIMES and GREETING have been replaced, and the #define lines themselves have disappeared. We used tail because the full output starts with the entire contents of stdio.h (and everything it includes): hundreds of lines of declarations. Running gcc -E is the best way to debug a confusing macro.

Function-like macros

A macro can take parameters. There must be no space between the name and the (, otherwise it's an object-like macro whose text starts with a parenthesis:

It looks like a function call, but nothing is called: the argument text is pasted into the replacement. That makes macros fast and type-agnostic, and it's also the source of every macro pitfall.

Pitfall 1: missing parentheses

Because substitution is textual, operator precedence applies to the expanded text. Every parameter use needs parentheses, and so does the whole replacement. Run this and work out each result by expanding the macro by hand:

SQUARE_BAD(1 + 2) expands to 1 + 2 * 1 + 2, which is 5, not 9. 100 / SQUARE_MEH(5) expands to 100 / (5) * (5), which divides first and gives 100, not 4. Fully parenthesised, both are correct.

Prefer functions; reach for macros when you need them

A static inline int square(int x) { return x * x; } evaluates its argument exactly once, is type-checked, and is just as fast with optimisation on. Macros are still the right tool when you need things a function can't do: work with any type, use __FILE__/__LINE__ of the caller, turn code into a string, or compute something the compiler needs as a constant (like ARRAY_LEN, which you'll write below).

Conditional compilation

In real projects you don't edit the source to turn debugging on; you define the macro from the command line with -D:

gcc -DDEBUG -Wall -Wextra main.c -o app

#error stops compilation with your message. You've also been relying on conditional compilation without knowing it: assert from <assert.h> is a macro that disappears completely when NDEBUG is defined, which is how release builds turn assertions off.

Predefined macros

The compiler defines some macros for you:

NameExpands to
__FILE__the current source file name, as a string literal
__LINE__the current line number, as an integer
__DATE__, __TIME__when the file was compiled, as strings
__STDC_VERSION__the C standard in use, e.g. 201710L for C17
__func__the name of the enclosing function (see below)

Strictly speaking, __func__ isn't a macro: the preprocessor doesn't know what a function is. It's an identifier the compiler declares at the start of every function body, as if you'd written static const char __func__[] = "function-name";. That's why the debug macro above could use it to print the name of the function that called DEBUG_LOG.

Multi-file programs

Real programs aren't one file. Splitting code into modules keeps related code together, lets several programs reuse a module, and means a change to one file only requires recompiling that file. C's model for this is simple and is built on what you just learned:

  • A header (.h) contains declarations: function prototypes, type definitions (structs, enums, typedefs), macros, and extern declarations of shared variables. It's the module's public interface: what it offers.
  • A source file (.c) contains the definitions: function bodies and the variables themselves. It's how the module works.
  • Any file that wants to use the module #includes its header, which pastes in the declarations so the compiler can check every call.

Declarations, definitions and extern

A declaration tells the compiler a name exists and what type it has. A definition actually creates it: allocates the variable's storage or provides the function's body. You can declare something as many times as you like, but across the whole program each function and global variable must be defined exactly once.

For functions, a prototype is automatically just a declaration. For variables you need extern: extern int vec_ops; means "there is an int called vec_ops somewhere else; let me use it". Without extern, putting int vec_ops = 0; in the header would define a separate variable in every file that includes it, and the linker would complain about multiple definitions.

static: keeping things private

At file scope, static means something different from the static local variables you may have seen: it gives a function or global variable internal linkage, making it invisible outside its .c file. square in vec.c is a helper nobody else should call, so it's static. That keeps the module's interface small, and another file can have its own square without a clash. A good default: make every function static unless it's in the header.

Include guards and #pragma once

Headers often include other headers, so the same header can easily be pasted into one .c file twice (say, main.c includes vec.h and shapes.h, and shapes.h also includes vec.h). Prototypes can be repeated harmlessly, but defining the Vec type twice is an error. The include guard pattern prevents it:

Pick a guard name unique to the file, usually derived from its name. Most compilers (GCC, Clang, MSVC) also support the one-line #pragma once at the top of a header, which does the same job. It isn't part of the C standard, but it's so widely supported that many projects use it. Either is fine; just be consistent, and give every header one.

Compiling and linking

Building a C program is really two steps. The compiler turns each .c file, on its own, into an object file (.o) of machine code. Calls to functions in other files are left as unresolved references. Then the linker combines the object files and libraries into one executable, connecting each call to its definition.

gcc -std=c17 -Wall -Wextra -c vec.c        # compile only: produces vec.o
gcc -std=c17 -Wall -Wextra -c main.c       # produces main.o
gcc main.o vec.o -o app -lm                # link (-lm: the maths library for sqrt)
./app
a + b = (4, 2)
2a = (6, 8)
|a| = 5
3 vector operations

For small projects you can do it all in one command, gcc -Wall -Wextra main.c vec.c -o app -lm, which compiles both and links them. Note that you never compile the .h files: they get compiled as part of every .c that includes them.

Knowing the two steps makes the two classic errors easy to read:

  • undefined reference to `vec_add' is a linker error. Something called vec_add, and the header promised it exists, but no object file defined it. You probably forgot to compile or link vec.c, or misspelled the function in the definition.
  • multiple definition of `vec_ops' is also a linker error: two object files both defined it. Usually that's a variable (or a non-static function body) defined in a header.

Exercises

Fix the MAX macro

The MAX macro below is missing parentheses, so some of the results are wrong. Fix the macro (and only the macro) so the program prints the correct maximum on every line.

Hint

Expand 10 * MAX(1, 2) by hand: 10 * 1 > 2 ? 1 : 2, which compares 10 with 2 and yields 1. Put parentheses around every use of a and b, and around the whole replacement.

An ARRAY_LEN macro

Define a macro ARRAY_LEN(arr) that evaluates to the number of elements in an array, for any element type. The calls are already in place, so you only need to write the macro. (This only works on real arrays, not on pointers. Think about why.)

Hint

The whole array's size divided by one element's size: (sizeof (arr) / sizeof (arr)[0]). greeting is 6 because the array includes the '\0'. Inside sum, a is a pointer, so sizeof a would be the size of a pointer, which is why the length has to be computed where the real array is visible.

Switchable debug macros

When DEBUG is defined, DEBUG_PRINT(msg) should print [debug] <function>: <msg>, and DEBUG_INT(expr) should print [debug] <function>: <expr as written> = <value>, both to stdout. When DEBUG isn't defined, both must expand to nothing useful (the #else branch is done for you). Use __func__, the # operator and do { } while (0).

Hint

__func__ is evaluated where the macro is expanded, so it names the calling function. #expr turns the argument into a string, so DEBUG_INT(total * 2) can print "total * 2". Something like do { printf("[debug] %s: %s = %d\n", __func__, #expr, (expr)); } while (0).
